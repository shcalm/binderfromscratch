    第 02 章设计决策：受控设备入口¶

    问题与候选方案¶

    Socket 已完成一次 RPC，现在选择内核管理通信状态，需要一个进程能进入驱动的入口。此时不实现请求排队，先证明入口本身的生命周期和边界可解释。

    read/write 适合字节流，但必须另行约定命令、长度和分帧。ioctl 用命令号区分操作，适合查询/注册/提交等设备协议；其代价是 ABI 布局和兼容性必须长期管理。当前选择 ioctl，不意味着 Binder 的每个 BC/BR 命令都是独立 ioctl。

    注册使用 miscdevice，它仍是字符设备，通过 VFS/file_operations 工作；省略手工申请主次设备号不影响核心问题。设备 /dev/mini_binder 默认仅拥有者可读写，实验在 VM root 内运行。

    首版 ABI¶

    include/uapi/mini_binder.h 定义版本 1 和 MB_IOC_QUERY。查询输出为固定 24 字节：u32 版本、u32 能力位、u64 打开上下文标识、u64 当前存活上下文数。没有裸内核指针，没有依赖 long 或 size_t 的字段，也没有输入字段。

    未知命令（包括编码长度不匹配）返回 ENOTTY；不可写用户输出地址返回 EFAULT；不属于打开进程的操作返回 EPERM。正确性不依赖先验证用户地址后直接解引用，复制通过 copy_to_user 完成。

    这是 Linux x86_64 教学 ABI，当前不提供 compat_ioctl 或 Android libbinder 兼容性。结构扩展通过明确的新命令/版本完成，不能悄悄改变已有命令字段。

    打开上下文与所有权¶

    • 一次成功 open 分配一个上下文和单调递增调试标识，同时持有打开进程的 struct pid 引用。
    • 相同进程再次 open 得到独立上下文；dup 和 fork 继承的是同一个打开文件对象，不重新触发 open。
    • 同进程的线程和 dup 可以操作同一上下文。fork 子进程持有 fd，但 ioctl 明确返回 EPERM，需要自己重新 open。
    • 身份校验比较进程的 struct pid 对象，保留引用避免 PID 数字复用导致误判；它不是后续服务权限策略的替代品。
    • 最后一个文件引用释放时调用 release，释放 pid 和上下文，减少存活计数；并非任意一次 close 都触发 release。
    • 暂无 mmap，未来加入后必须重新审计 VMA 对文件引用和上下文的持有，不能照搬“close 即释放”的简化。

    调试计数用于受控实验，不是并发场景的稳定全局快照，不用于授权或对象寻址。

    验收与 Android 对照¶

    VM 测试必须验证独立 open 的不同标识、dup 的相同标识、关闭部分 fd 后仍可查询、最后关闭后计数恢复、fork 子进程拒绝使用及可自行 open、错误指针与长度、未知命令。模块初始化/卸载由 VM 日志观察。

    Linux v6.6 的 binder_open 也在 filp->private_data 保存驱动上下文，但真实 Binder 有事务、映射与延迟清理，不能将本章 release 的简单实现视为完整 Binder 退出语义。具体源码定位将在正文核查并链接。
