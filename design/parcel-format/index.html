    第 05 章设计决策：普通字段与特殊对象分开¶

    状态：开发实现已完成 TCG/KVM 验收，证据与边界见阶段报告，尚未正式发布。沿用第 04 章接收映射及固定整数回复；本章不增加变长回复、Node、Ref 或 FD 转换。已确认的教学路线要求先解释设计，再用实验验证，最后对照固定版本 Android 源码。本文件记录本章具体选择，不把未来能力视为已经支持。

    1. 新需求为什么不能靠 memcpy(struct) 满足¶

    第 04 章能把 1–4096 个字节送到只读接收页，却没有规定如何理解这些字节。新请求包含序号、状态、可为空的字节串和变长 int32 数组。含指针的 struct 复制后仍引用发送进程地址；即使在同一进程，浅复制也会继续别名原数据。改成共享地址不能自动解决长度、对齐、版本和所有权问题。

    候选方案 合理用途 本次选择与成本
    固定大小消息，内嵌字符与数组 字段和容量永远固定时简单可靠 变长数据必须预留最大空间，增长需求会扩大每次消息；保留为可行替代。
    JSON 或其他成熟编码 现有库、可读性和跨语言生态优先的业务 可以用于真实服务；本章要逐字节解释边界和内核特殊资源索引，故选择小型教学编码，不以性能优越为理由。
    明确长度的二进制字段流，特殊对象另给偏移表 能独立推导普通字段与内核描述符的职责 采用；代价是自行定义格式、版本、校验，并承担测试和维护，不宣称兼容 Android Parcel。

    2. 普通数据格式与用户态接口¶

    普通模型使用 MBP1 四字节魔数，随后 little-endian u32 版本 1。固定示例 schema 为 u32 sequence、i32 status、nullable bytes label、i32 array values。字段顺序由客户端和服务端共同约定；魔数和版本不能自动发现字段类型，也不提供任意向前兼容。

    所有数值显式编码为 4 字节，不强转未对齐指针。bytes 写 u32 长度、原始字节及补至 4 字节的零填充；0xffffffff 单独表示 null，长度 0 表示空串。字节串允许嵌入 NUL 和非 UTF-8，不是 C 字符串，不添加终止符。数组写 u32 个数和各 i32；本 schema 数组没有 null。整条消息不超过 4096 字节，拒绝额外尾字节、未知版本、非零填充、截断和无法容纳的长度/计数。先做减法边界检查，再乘以元素大小。

    用户态库分别提供 writer/reader 的初始化、u32/i32、bytes、i32 数组与结束检查。字段读写失败不推进该次操作的游标；调用方检查每次返回值，整条业务消息失败后不得使用部分结果。reader 只借用接收页，FREE 后所有借用指针失效；需要延后处理时先复制到应用存储。

    3. 为什么给对象单独的偏移表¶

    驱动不应扫描普通字段猜测“这个整数是否是 Handle”，也不需要理解 label。特殊对象若将来携带内核资源，则必须让驱动确定描述符位置、核对类型并执行转换。偏移表仅列出特殊对象，不列普通字段；这是两个不同层次的协议。

    新增 mb_parcel_call 为 32 字节：u64 data、u64 offsets、u32 size、u32 offsets_count、u32 result、s32 status。新增 MB_IOC_CALL_PARCEL，保留全部旧命令；QUERY 新增 MB_FEATURE_PARCEL 表示此传输包络与校验能力，不能解读为 Node/Ref 已实现。普通无对象请求必须 offsets=0、offsets_count=0；此时经既有 REGISTER_BUFFER/RECEIVE_BUFFER 交付，回复仍走 REPLY 的整数结果。

    教学 offsets 是最多 16 个 u32 数据区字节偏移；Android 的 binder_size_t 数组和 offsets_size 字节计数与此不兼容。每项必须 8 字节对齐，严格递增且不重叠，范围内至少容纳 8 字节 mb_object_header（u32 type、u32 flags）。头部采用当前 x86_64 UAPI 的固定宽度字段，与普通数据显式 LE 编码区分。后续真正实现对象时需按类型验证完整结构大小和资源归属，不能把当前最小头校验当成完整描述符验证。

    本章没有任何可转换对象类型。所有偏移项先完成边界/顺序校验；只要有结构合法的对象项，就返回 EOPNOTSUPP，不入队。不合法包络/偏移返回 EINVAL，用户地址复制失败返回 EFAULT。先检查 offset <= size，再检查 size - offset >= 8；先检查 count <= 16，再计算表大小。没有凭空接受“Node 地址”或“Handle 数字”。重叠/乱序等结构错误优先于“不支持类型”，包括第一项合法而后项重复或越界的情况。

    这些规则只适用于 CALL_PARCEL 显式声明的特殊对象表。保留的 CALL_BUFFER 仍是普通字节通道；不列入表的“看似对象头的字节”不会成为内核对象。Server 必须始终验证自己的业务格式。

    4. 快照、发布与回滚¶

    1. 复制控制结构，检查长度/表大小/无对象时的规范空指针，复制至多 64 字节偏移表到内核栈。
    2. 按已有 Server 模式、容量与调用资格规则取得 mb_lock，预留目标槽。
    3. payload 直接复制到接收 backing，随后只验证这个内核副本中的描述符；不重复读取发送方 payload 做安全决定。发送者仍不得并发修改输入；这不保证任意并发写入下的原子业务快照。
    4. 校验失败直接归还预留槽，不创建请求或唤醒接收者；不能调用只适用于已入队事务的 mb_finish，也不修改 busy/queued/live_requests。成功后按第 04 章语义入队、领取、回复和显式释放。

    成功复制计数延用第 04 章“成功发布的 payload”口径；被校验拒绝的实际复制不会计入成功发布次数。所有拒绝路径用请求/槽账目确认回滚，不能仅看错误码。偏移表和控制结构的复制仍存在，没有新增零复制结论。接收者已映射整个 backing，可能直接观察未发布槽里的写入；不入队保证的是不返回描述符和不授予使用权，不是字节保密。若要保证验证前不可见，需要额外 staging copy 或更复杂的映射发布机制，本章不提供该保证。

    持锁与映射生命周期沿用接收区设计。新验证在有界的内核缓冲和至多 16 项表上运行，不新增锁；大锁跨用户复制的缺页阻塞成本仍保留。

    5. 实验及 Android 对照¶

    • C 浅复制反例只在合法同进程地址上观察别名，不通过随意解引用外进程地址制造未定义行为。
    • 独立 Python struct 编码 oracle 检查整串字节；遍历每个截断前缀，包含 null/空串、NUL、符号边界、精确 4096 字节和超长输入。
    • VM 在映射接收页解码正常请求与恶意普通字段；后者由 Server 返回业务错误并 FREE，驱动并不越层解析。每次之后检查槽、请求恢复。
    • VM 检查偏移错位、越界、UINT32_MAX、重复、乱序、不支持对象、错误 offsets 指针和部分复制失败；拒绝之后正常请求仍可完成。
    • 保留旧 RPC、映射及退出回归；没有动态覆盖的路径在报告逐项列明。

    固定对照为 AOSP Android 14 用户态基线与 Linux v6.6 驱动基线：Parcel::writeAligned/writeString16/writeObject 负责普通编码与对象索引，IPCThreadState::writeTransactionData 分别提交 data/offsets，binder_transaction/binder_get_object 校验并转换特殊对象。两套来源是阅读输入，不是已验证的 Android 运行组合。正文必须逐项标明教学魔数、字节串、端序、表元素宽度、拒绝所有对象及固定回复等简化。
