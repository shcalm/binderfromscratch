    第 03 章设计：一台服务端与同步请求/回复¶

    为什么上一版不够¶

    第 02 章只能查询打开上下文，无法把工作交给另一个进程。现在要求独立启动的 Server 注册为接收方，多个 Client 调用 add，各自等待自己的结果。

    单槽邮箱简单，但两个 Client 同时提交时必须覆盖、拒绝或等待；没有回复关联就可能把 A 的结果交给 B。忙轮询队列可以工作，但没有请求时仍消耗 CPU。当前选择有界请求队列、每笔最小记录和等待队列，不提前加入对象寻址。

    范围与命令¶

    同一设备只允许一个注册 Server。每次 open 的上下文至多一笔同步调用；独立 open 可并发。继承 fd 的外进程仍被拒绝，线程可共享打开上下文。注册的同一上下文不允许 CALL 自己，返回 EDEADLK；同进程另一次 open 不受此检查保护，若没有其他接收线程仍会死锁。此时没有第 10 章的调用链路由。

    新增 REGISTER、CALL、RECEIVE、REPLY、STATS。CALL 输入 a/b，成功交付后返回独立的业务状态和结果；RECEIVE 返回请求标识与参数；REPLY 由注册者携带请求标识、状态和结果。unknown/stale ID 返回 ENOENT，非 Server 回复返回 EPERM，重复注册/同上下文重复调用返回 EBUSY，无 Server 返回 ENOTCONN，全局 64 笔资源耗尽返回 EAGAIN。

    状态区分：排队（等待领取）、已交付（等待回复）、已完成（结果或通信错误已确定，等待调用线程取走）。请求由 CALL 线程分配和最终释放，Server 只在锁保护下查找它，不能保存生命周期无保证的裸指针。

    同步与回收¶

    早期选择一把可睡眠 mutex 保护注册者、请求链表、状态和计数；两类等待队列分别用于服务端接收工作和调用者等待结果。先持锁检查条件，再通过 wait_event_interruptible 重新检查条件和睡眠，不把一次 wakeup 当作已有工作。

    固定大小 RECEIVE 的 copy_to_user 暂在 mutex 内进行，只有复制成功才将请求从排队改为交付，因此 EFAULT 后仍可重试领取。mutex 允许睡眠，不能替换成 spinlock 原样运行。代价是故意延迟用户页故障可能阻塞其他操作；第 15 章要用显式保活与更细粒度边界改进，当前不作抗恶意阻塞保证。

    CALL 的输入在入队前复制；结果在完成并从全局表移除后复制。若最后输出复制失败，返回 EFAULT，但远端可能已经执行，重试不是业务恰好一次保证。

    • Client 等待被信号打断且请求尚未完成：删除记录，返回 EINTR 路径；Server 可能已开始业务，不能保证取消副作用。
    • CALL 不向系统调用层返回可自动重启的 ERESTARTSYS，而转换为 EINTR；即使安装 SA_RESTART 的处理函数也不能默默创建第二笔业务请求。RECEIVE 尚未领取工作时重启等待则不会重发业务。
    • 回复与信号竞争：持锁时若完成已提交，就按已完成结果返回；否则中断移除，请求的迟到回复收到 ENOENT。
    • Server 最后一个文件引用释放：将尚未完成请求设为 EPIPE 并唤醒。排队和已交付请求都结束。
    • 请求完成与移除分别记账，Server 退出不能重复完成已回复请求。

    通信上下文的寿命跟随打开文件引用，不是 PID 死亡瞬间。若 fork 子进程保留继承的 fd，即使不能操作，也可能延迟最终 release；实验要求继承端点及时关闭。当前不提供独立的进程死亡回调，这个差异要在生命周期章节深化，不能把本章 last-close 行为称为完整死亡通知。

    阻塞中的 ioctl 本身也持有文件引用。另一个线程关闭最后用户 fd 不一定马上触发 release，更不能靠它取消仍在等待 RECEIVE 的线程；需要中断或终止执行线程。后续线程与生命周期模型必须正面处理这一点。

    验收与真实 Binder 对照¶

    使用独立进程和管道握手控制已注册、已领取、回复许可。STATS 仅用于受控实验观察排队/交付/存活记录，等待条件有截止时间，不能把 sleep 后碰巧观察到结果作为证明。

    必须覆盖多 Client 不串回复、无 Server、注册冲突、伪造回复、输出 EFAULT 后重领、排队/领取后 Server 退出、Client 信号中断和迟到回复。结束后请求计数归零。

    Android Binder 也需要工作交付、同步等待与回复关联，但真实版本有目标 Node/Ref、线程栈和四种 BC/BR 事件，本版阻塞 CALL 并非协议兼容。请求 ID 是教学相关机制，不能声称它就是完整 binder_transaction 的全部职责。
