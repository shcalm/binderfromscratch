# 从含指针 struct 到有边界的字节消息

对应 C05-01、C05-02。固定消息与 CLI 是 [模型](../../examples/models/parcel.c)，共用编解码实现是 [用户态库](../../userspace/parcel.c)，公开契约见 [parcel.h](../../userspace/parcel.h)。验收包含独立字节 oracle 的 [模型测试](../../tests/test_parcel_model.py) 和直接调用库的 [API 测试](../../tests/test_parcel_library.py)。本页普通 C 实验定义自己的格式，不打开 mini-binder 设备，不修改驱动或 UAPI，也不兼容 AOSP Parcel 或 Binder ABI。

## 需求与反例

第 04 章使接收者能访问一段有长度的接收字节区，但这些字节仍需要双方共同解释。假设请求含 u32 序号、i32 状态、一个可以为 NULL 的字节串和一个变长 i32 数组。字段值必须跨地址空间保留，接收者不能依赖发送者的指针、C struct 布局或本机字节序；对错误输入也必须有明确边界。

固定 struct 是合理的起点。双方只传两个 u32、使用同一受约束 ABI 时，字段少、访问直接，不必先构造通用序列化框架。也可以把字符串和数组改成固定容量内联数组，附长度字段并逐一校验：这样没有进程指针问题，但最大容量会进入协议、短消息仍占固定空间，字段变化需要约定版本。结构体 padding、字节序和整数宽度仍须独立规定，不能仅因两边都使用 C 就假定线上的裸内存布局稳定。

含指针的 struct 又多一层问题：复制 struct 只复制地址数值，不复制地址所指的字节串和数组。`raw` 模式在同一个进程中用 `memcpy` 复制含两种指针的 struct，修改原字节串和原数组后，副本仍通过相同指针看到修改。它同时在修改之前编码一份字节消息，展示编码结果不再依赖原指针：

```text
same_label_pointer=1
same_array_pointer=1
raw_label_before=410042
raw_label_after=5a0042
raw_array_after=99,-2
wire_label=410042
wire_values=1,-2
```

该实验没有故意解引用另一个进程的指针；它确定地证明了 struct 的复制不会深复制指向的数据。跨进程时，相同地址可能没有映射，也可能指向不同对象，即使 fork 后暂时有同地址内容，也不能把这个巧合当作 IPC 协议。指针本身的字节数、padding 等也不会为接收者携带正确的字段长度。

## 候选方案与决定

| 方案 | 合理用途 | 此处取舍 |
| --- | --- | --- |
| 固定容量内联消息 | 字段少、容量固定、两端协议同时更新 | 容易验证，保留为合理选择；本例需观察 NULL、空串和不同长度数组，选择显式长度字段 |
| JSON 等文本格式 | 人工检查、多语言交互、已有成熟解析器 | 可用，但需要明确整数范围、二进制字符串编码及解析资源限制；不是本例要隔离的机制 |
| 定宽整数加长度前缀的二进制格式 | 已知字段类型、明确大小上限、可逐字节检查 | 本例选择；牺牲可自由添加字段的灵活性，换取小而可检验的格式 |

本例固定字段顺序，以 magic 区分格式、version 拒绝不认识的版本。它没有 TLV 或未知字段跳过规则，因此不能宣称实现了可任意扩展的通用协议；增加字段需要另定义版本和兼容策略。四字节对齐是协议选择，便于观察 padding 和数组边界，不是所有 CPU 或所有二进制协议都必须如此。即便起始缓冲地址未对齐，解码也只按字节组合整数，不把用户输入指针 cast 成 `uint32_t *` 或 `int32_t *`。

## 线上的格式

一条完整消息最多 **4096 字节**，包括头、长度前缀和 padding。运输层或调用者提供消息总长度；格式里没有另一份总长度字段。以下整数均按 little-endian 写成四个字节；i32 使用 32 位二进制补码的线表示。

| 顺序 | 字段 | 规则 |
| --- | --- | --- |
| 1 | magic，4 字节 | 固定 ASCII `MBP1`，即 `4d 42 50 31` |
| 2 | version，u32 | 必须等于 1；magic 中的字符 1 只是固定 magic 的一部分 |
| 3 | sequence，u32 | 范围 0–4294967295 |
| 4 | status，i32 | 范围 −2147483648–2147483647 |
| 5 | label 的长度，u32 | `ffffffff` 表示 NULL，此时无字节和 padding；0 表示非 NULL 的空字节串 |
| 6 | label 的数据与 padding | 恰好 length 字节，然后补 0–3 个零字节，使数据长度补齐到 4 的倍数；length 不包含 padding |
| 7 | values 的个数，u32 | 数组可以为空，不支持 NULL 数组；`ffffffff` 不是 NULL 数组标记 |
| 8 | values 的各元素，i32 | 按顺序每元素 4 字节；count × 4 必须经过溢出与容量检查 |
| 9 | 结束 | 必须恰好用完输入；任何剩余字节都拒绝 |

label 是**字节字符串**。不自动添加末尾 NUL，不以 `strlen` 决定字段长度，允许嵌入 NUL 和非 UTF-8 字节；本模型不验证 UTF-8，也不把它解释成 C string。CLI 以 hex 显示 label，避免 NUL 截断终端输出或不可打印字节造成歧义。

`demo` 的布局是 44 字节：

| 偏移 | 字节 | 含义 |
| --- | --- | --- |
| 0 | `4d425031` | magic |
| 4 | `01000000` | version 1 |
| 8 | `78563412` | sequence 0x12345678 |
| 12 | `f9ffffff` | status −7 |
| 16 | `03000000` | label 长度 3 |
| 20 | `410042` | `A`、NUL、`B` |
| 23 | `00` | 一个 padding 零字节 |
| 24 | `04000000` | 数组元素数 4 |
| 28 | `01000000 feffffff ffffff7f 00000080` | 1、−2、INT32_MAX、INT32_MIN |

不检查非零 padding 会使同一字段值对应多种任意填充值，也可能掩盖边界错误；本例把全零 padding 作为必须满足的格式规则。

## 运行与观察

前置条件是支持 C11 的 C 编译器、Python 3 和普通用户态进程环境；不需要 root、设备、VM 或网络。在仓库根目录运行：

```sh
mkdir -p build
cc -std=c11 -O2 -Wall -Wextra -Werror -pedantic -Iuserspace examples/models/parcel.c userspace/parcel.c -o build/parcel
./build/parcel raw
./build/parcel demo
./build/parcel selftest
python3 -m unittest discover -s tests -p 'test_parcel*.py' -v
```

前三种有效模式都应返回 0。`raw` 输出应匹配前述别名实验；`demo` 必须得到确定的字节和往返字段：

```text
hex=4d4250310100000078563412f9ffffff03000000410042000400000001000000feffffffffffff7f00000080
sequence=305419896
status=-7
label=410042
values=1,-2,2147483647,-2147483648
```

也可以让 Python 或其他实现生成 hex，再交给模型独立解码；以下示例不依赖模型自己的编码结果：

```sh
./build/parcel decode 4d4250310100000078563412f9ffffff03000000410042000400000001000000feffffffffffff7f00000080
./build/parcel encode 305419896 -7 410042 '1,-2,2147483647,-2147483648'
./build/parcel encode 1 -1 null ''
./build/parcel encode 1 -1 '' ''
```

`decode` 输出四个字段、不再输出 hex；`encode` 只输出 `hex=...`。最后两个命令分别输出 NULL 与空串的消息：

```text
hex=4d4250310100000001000000ffffffffffffffff00000000
hex=4d4250310100000001000000ffffffff0000000000000000
```

CLI 整数是十进制，不接受越界值、空整数或正号；数组是逗号分隔的 i32，不允许尾逗号或空元素。空参数 `''` 表示空数组或空字节串，字面量 `null` 仅用于 label。hex 不接受空白或 `0x` 前缀，大小写均可；空 hex 虽是合法的零个字节，作为完整消息仍因截断而拒绝。

## 错误与自动验收

未知命令或参数个数错误返回 2，并向 stderr 输出 `usage:`。输入数据、格式或容量错误返回 1，stderr 包含 `error=原因`，stdout 必须为空。预期错误命令例如：

```sh
./build/parcel decode 4d425031
./build/parcel decode 4d42503102000000
./build/parcel decode 4d4250310100000078563412f9ffffff03000000410042010400000001000000feffffffffffff7f00000080
./build/parcel decode 4d4250310100000001000000ffffffffffffffffffffffff
```

以上分别必须返回 1，原因是 `truncated`、`version`、`padding`、`limit`。脚本若启用 `set -e`，需显式处理这些预期退出 1。任何意外成功、异常信号、挂起、错误输出却返回 0，均为失败。

九项模型测试使用 Python 标准库 `struct.pack('<I', ...)`、`struct.pack('<i', ...)` 和独立 padding 规则作为 oracle，不能只因 C 编码器和 C 解码器彼此吻合就算格式正确。测试会比较完整 hex，同时把 Python 生成的消息送进 C 解码器，覆盖整数端点、27 组确定性字段组合、NULL/空串/嵌入 NUL/非 UTF-8 字节、44 字节示例的每一个不完整前缀、错误 magic/version、非零 padding、恶意长度/计数和剩余字节。另有八项 API 测试，直接链接库，验证初始化失败、调用方数组容量与保护字、未对齐基址、非零游标、可选 error 指针和字段输出的提交规则；合计十七项必须全部通过。

上限测试分别构造 4072 字节 label 加空数组、NULL label 加 1018 个 i32，消息都恰为 4096 字节；再增加一个 label 字节或数组元素则必须拒绝。长度 `fffffffe`、数组计数 `40000000` 或 `ffffffff` 也必须拒绝，不能先以 u32 做会回绕的加法或乘法，再把小结果当作合法尺寸。在 64 位 size_t 下部分恶意值未发生机器整数溢出，但仍超过协议上限；较窄平台可能先报告 `overflow`。不能以某次错误名称代替完整的边界检查。

测试先在临时目录编译并于结束时清理，每次执行的 timeout 为五秒，编译为三十秒。测试超时即失败，不以速度变化推断消息复制次数。代码没有进程、线程、sleep、持久文件或后台清理任务；手工编译产物可用 `rm -f build/parcel` 删除。

## 游标与所有权约定

模型不再自行实现整数或变长字段编码，统一调用用户态库；固定字段顺序仍留在模型的 `encode/decode` 中。库本身不识别 sequence、status 或 label 等业务字段，调用双方必须事先约定 schema；magic/version 只约束这里的编码规则，不会自动协商任意业务格式。

| API | 契约 |
| --- | --- |
| `mbp_writer_init` / `mbp_reader_init` | 写入/检查 MBP1 与 LE version 1；容量/长度包含头且最多 4096，成功游标为 8，失败不提交游标对象 |
| `mbp_write/read_u32` / `mbp_write/read_i32` | 一次处理一个四字节整数；失败不推进游标，不修改读出值 |
| `mbp_write/read_bytes` | 写入借用调用期间的源字节；读出指向 wire 的 const 视图、size、is_null，全部校验后一起提交 |
| `mbp_write/read_array` | 写入借用源元素；读取复制到调用者提供的数组，capacity 单位是 i32 元素，count 是输出值 |
| `mbp_writer_finish` / `mbp_reader_finish` | 成功返回已编码总长度，或确认没有剩余输入；reader 的 finish 不会自动跳过尾部数据 |

所有 API 成功返回 1，失败返回 0；可选 `const char **error` 在失败时得到静态原因字符串，成功不修改它。数组读取先校验 count × 4、剩余输入、调用方 capacity 和必要指针，才写第一个元素；容量不足时数组原内容、count 和游标都保持不变。NULL 数组输出指针仅用于读取空数组。调用者需要提供有效且不重叠的源、目标、游标和输出存储；库不能验证任意非 NULL 地址实际可访问。

通用库只带八字节头时，单个 bytes 字段可容纳 4084 字节，单个 i32 数组可容纳 1021 个元素；模型还带 sequence、status 和另一变长字段，因此本页前述 4072/1018 是该 schema 的上限。库的最大 payload 仍是 4096，没有因抽取库而放宽。

读写游标先检查当前位置是否在缓冲内，再用 `count <= size - position` 判断剩余容量，避免先做可能溢出的 `position + count`。所有长度相加、数组 count × 4 和 `(length + 3)` 补齐运算均有 size_t 溢出检查，随后再检查协议上限。读整数通过逐字节移位组合；写整数也逐字节输出，不依赖主机端序或未对齐整数访问。负数按无符号模转换编码；解码时通过有界算术恢复 i32，避免把大于 INT32_MAX 的无符号值直接转为有符号值。

每个有前缀的字段用临时游标，只有完整校验和读写成功后才提交；模型的完整消息也采用同样规则。失败时调用者游标保持原位置；CLI 不输出部分消息。这里保证的是游标提交语义，并未为通用调用者承诺失败时 writer 输出缓冲中的每个字节都未被触碰。解码器只在整条消息成功后赋值输出 message。`selftest` 断言十项失败后的游标不推进，涵盖原语截断、长度/乘法溢出、错误 padding、编码容量不足和头部版本失败；另通过公开字段 API 传入 SIZE_MAX 附近的长度与计数，断言四项 size_t 溢出拒绝，不实际访问如此大的对象。API 测试独立确认失败时读出标量、字节视图和数组不会公布部分输出。

编码输入是调用者已拥有且在调用期间稳定的有效内存，模型不验证任意 C 指针是否可读，也不处理另一线程同时修改源对象的竞态。解码后的 label 是指向输入 wire 缓冲的只读视图；调用者必须保留该缓冲，修改它也会改变视图内容。数组元素则复制进输出 message 的固定容量存储。这个不同的所有权约定必须说清，不能把一次解码成功等同于产生了完全独立的深拷贝对象。

## 与后续 Binder 问题的边界

本模型只包含普通字节与整数，没有 Binder 特殊对象、对象偏移表、FD、Handle、Node/Ref、服务接口分发或异常协议。输入长度由 CLI 提供，模型未连接驱动 CALL_BUFFER，也没有验证接收槽释放或内核描述符的生命周期；第 04 章的缓冲 token 不能因为某些字节看起来像地址就自动成为这里的指针字段。

已确定的 AOSP 后续对照基线为 `android-14.0.0_r1` 的 `frameworks/native` 提交 `bfcf75076e562945bae131a4929f29a90d0d2481`。本实验未据该基线逐段核查 Parcel 源码，因此不在此提供未验证的函数对应或行号，也不宣称其字符串、对齐、NULL 或对象规则与本格式一致。下一步需要分别设计用户态编解码边界和驱动识别特殊对象的边界，并在真正接入接收区后检验失败时的缓冲归还。
