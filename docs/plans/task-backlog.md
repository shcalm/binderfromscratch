# 《从零设计 Binder》全项目任务总表

更新日期：2026-11-06。

## 1. 使用规则与完成标准

本表是全项目任务状态的统一入口，覆盖 4 章预备篇、18 章正文、实验基础设施、网站、可视化与电子书。[路线图](roadmap.md)说明整体演进，[第一阶段计划](phase-01.md)补充早期执行细节，[教学规范](../design/teaching-contract.md)约束内容质量。

- `[x]` 只表示该条描述的交付物已经完成；初稿完成不表示整章通过验收。
- 每项有稳定 ID，后续提交、实验报告与问题记录引用该 ID；新增任务追加，不复用已删除编号。
- 任务完成时记录对应文件、代码提交或测试报告。当前已完成项以现有文件作为证据，尚未建立发布标签。
- 每章按“问题反例 → C 模型 → 必要内核知识 → 方案比较 → 增量实现 → 实验 → Android 对照 → 正文验收”推进。代码可以先验证可行性，正文不能倒置设计推导。
- 本表是可执行的工作分解，不提前定死后续章节的 ABI、锁或数据结构。对应章节的设计任务需要明确这些决定，不能只交一句“按 Binder 实现”。
- 任务实施时再按文件和测试拆成小步骤；未经实现与验证的能力不得标为支持。

### 所有章节共同的发布门槛

各章末尾的“验收”任务必须同时满足以下条件，不能只检查编译：

1. 读者能说明新增需求、上一版的限制、至少两个合理候选方案、选择理由和代价。
2. 关键机制有实验支撑；包含命令、预期结果、失败判据、观察证据、清理步骤和结论边界。
3. 内核/API 知识在使用前得到解释，指针、锁、阻塞、错误、所有权和退出路径有明确语义。
4. Android 对照绑定源码版本，区分驱动、libbinder、服务管理器，明确教学简化。
5. 完整代码可定位，前后 diff 可阅读，上一阶段测试无回归；初学者复现记录中的问题已处理。

## 2. 依赖顺序与交付物约定

| 阶段 | 依赖 | 输出与门槛 |
| --- | --- | --- |
| 基础规范 G / 实验设施 E | 无 | 教学标准、版本基线、统一运行和取证方式 |

| M2：04–06 | M1 | 映射、序列化、事务及资源账目成立 |
| M3：07–09 | M2 | 三进程对象传递、调用与释放闭环 |
| M4：10–12 | M3 | 嵌套调用、FD、死亡通知及竞争验收 |
| M5：13–15 | M4 | 授权、oneway、压力与故障注入 |
| M6：16–18 | M5、固定真实 Binder 环境 | 完整源码阅读和架构差异审计 |

P03 在阅读顺序上位于 P04 之前，但执行时先准备 P04 的环境，并给 P03 读者提供可验证的预构建镜像入口。第 16–18 章不是前面章节做 Android 对照的前置条件。

计划中的文件职责：`docs/chapters/` 保存正文，`docs/design/` 保存设计决策，`docs/labs/` 保存实验说明，`docs/reference/` 保存源码对照，`examples/` 保存 C 模型，`driver/` 和 `userspace/` 连续演进，`tests/` 保存验收，`tools/` 保存环境及运行工具。实验日志进入忽略的 `artifacts/`，可发布的摘要写入 `docs/reports/`。目录按需创建，不空建全部模块。
