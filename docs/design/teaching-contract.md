# 教学设计规范

## 目标与优先级

核心目标是让读者能够从需求推导设计。mini-binder 是可执行的设计模型，实验是检验推导的证据，Android Binder 是真实系统的对照。功能数量、代码规模和网站效果不能替代这三项。

读者起点是基本 C 语言知识。每次需要新的 Linux 概念时，先补充本章实际使用的那部分，再回到设计问题。允许读者先运行预构建实验环境，再学习如何构建它。

## 每章的论证链

1. **继承已有能力。** 指明上一版本已经能做什么，不能忽然抛弃它重写另一个无关 Demo。
2. **提出新场景。** 写成可以运行或明确推演的具体反例，不能仅以“真实 Binder 有这个功能”作为动机。
3. **模拟核心问题。** 使用普通 C 程序隔离一个概念，并说明它没有模拟真实内核的哪些条件。
4. **补充必要知识。** 解释 API 的前提、返回值、是否可能睡眠、资源归属，不只是列出 API 名称。
5. **比较至少两个合理方案。** 先指出简单方案能解决什么，再说明在新增约束下的不足。不得为证明 Binder 正确而贬低 Socket、共享内存等替代设计。
6. **写出设计决策。** 记录需求、被否决方案及理由、接口语义、状态变化、资源所有权和成本。
7. **增量实现与观察。** 展示关键差异，并提供完整可编译版本；每个重要结论指向实验或源码证据。
8. **回到 Android。** 关联真实协议、驱动和用户态实现，标注简化与不等价处，留下下一章的问题。

## 实验不能只是成功截图

每个实验包含：问题或假设、前置条件、准确命令、预期现象、失败判据、观察方式、结论、结论边界与清理方式。

按问题选择以下实验，而不是机械凑齐数量：

| 类型 | 例子 | 有效证据 |
| --- | --- | --- |
| 失败复现 | 直接把 B 的 Handle 数字交给 C | C 查到不同对象或收到无效引用错误 |
| 方案比较 | 拷贝接收与映射接收 | 两条代码路径和复制计数；性能数据另行解释 |
| 内部观察 | 多 Client 同时调用 | 请求标识、目标对象、线程和回复关联日志 |
| 边界验证 | Server 退出时仍有排队请求 | 等待者退出、资源计数归零、无重复完成 |

预期失败必须有确定的退出码或错误事件。自动实验有截止时间。并发测试不依赖随意 `sleep` 制造顺序，优先使用显式同步点。PID、地址、时间等不稳定字段不写死。

“同一地址不同值”不证明完整页表行为；“吞吐提升”不直接证明少了一次复制；“未崩溃”不证明没有泄漏。正文必须限制推论范围。

## Android 对照要求

每章维护一张表：教学问题、教学机制、真实源码入口、相同点、不同点、版本。函数名和协议名应从选定版本核查，不能凭记忆添加行号。

区分驱动和 libbinder：Parcel 的普通数据编解码、用户线程创建、服务方法分发不是内核驱动替应用执行的工作。对象/FD 转换与调用身份也不能混为普通字节传输。

每章只讲当前问题需要的源码片段。第 16–18 章负责完整架构和端到端调用链，不把前面各章变成提前展开的源码大全。

## 演进中的最低正确性

- 从第一个 ioctl 开始校验长度、整数运算、用户指针和调用者权限范围。
- 从第一个队列开始定义谁持有请求、谁可以结束它、退出时谁清理。
- 从第一个映射开始考虑 VMA 与打开文件的生命周期差异，不能认为 `close()` 必然销毁仍存活的映射。
- 锁不能覆盖可能睡眠但不允许睡眠的上下文；是否允许跨复制操作持锁必须明确分析。
- 第 12、13、15 章深化生命周期、安全和并发，不是这些正确性的首次出现。
