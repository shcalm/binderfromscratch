# 15｜同时调用、释放和退出时，账目怎样仍然成立

上一章：[异步事务](14-oneway.md) · 下一章：[真实 Binder 架构](16-binder-architecture.md)

Client B 正在向对象 X 提交请求，Client C 同时把另一个引用转交给 D；Server A 的线程归还 X 的旧缓冲，另一个线程则准备关闭服务。四条路径都要碰 Node、Ref、槽或事务表。若提交刚查到 X，退出路径就把 X 释放了；或者同一笔事务被取消和回复各结束一次，前面章节分别正确的代码仍会组合出悬空指针或重复归还。本章要为这些交错建立可以逐步检查的规则。

> **实现边界：**当前 [mini-binder](../../driver/mini_binder.c)只有 C08 能力，跨上下文元数据主要受 `mb_lock` 这个 mutex 保护；尚无第 09–14 章的多 owner 路由、真实线程模型、FD、死亡通知、安全策略和 one-way。本章先审查现有锁与回收，再提出后续分域设计和测试方法，不声称已经完成锁重构、压力验收、KASAN 或 lockdep 运行。

## 1. 先继承大锁提供的正确性，再谈并行

上一章的设计使一次 FREE 同时归还对象单位、槽和异步额度，还可能放行同 Node 的下一笔请求。只把每个计数改成原子变量，并不能使这些变化整体发生：另一个 CPU 仍可能看到“active 已清，但旧槽还活着”这样的中间状态。

现有 C08 用大锁把查表、固定目标、对象转换、提交和部分回滚串在一起。它很容易说明“先查到的 Node 为什么还活着”，也让取消与回复有一个明确先后。减少锁覆盖面以前，应先写出它已经保护的关系，否则性能优化可能悄悄删除正确性条件。

一个最小反例有三步：T1 在 Ref 表读出 `ref->node`；T2 删除最后一条 Ref 并释放 Node；T1 增加 Node 计数或读取 owner。T1 此时甚至还没来得及“增加引用”。所以安全持有必须在保护查找和删除的锁下取得，不能先拿裸指针，解锁后才尝试补引用。

## 2. 首次需要的知识：互斥、持有与一次提交

锁提供临界区互斥，引用提供跨越临界区的存活保证。持锁时能安全访问一个对象，不代表解锁后仍能访问；持有对象引用也不代表它的可变字段可以不加锁读取。两者回答不同问题。

Linux mutex 可以在获取时睡眠，适合可睡眠的进程上下文；普通 spinlock 的临界区不能执行可能睡眠的操作。`copy_from_user()`、`copy_to_user()` 可能因缺页阻塞，`GFP_KERNEL` 分配也可能睡眠，不能不加分析地塞进普通自旋临界区。

这里的“线性化点”指一个并发操作对其他参与者正式生效的瞬间。例如，成功提交是请求链接到队列且资源责任提交的时刻；取消和回复争夺的是同一笔事务的唯一终态。调用开始、唤醒、打印日志都不是自动的线性化点。

`READ_ONCE` 可用于等待条件的单次读取，但它不保活指针，不把一组字段变成一致快照，也不替代锁和必要的内存顺序。原子计数保证单个计数更新不可分，并不自动保护“找到对象、判断活性、增加计数”的完整协议。

## 3. 当前 C08 的锁域，先按真实代码核对

| 资源或路径 | 现有保护 | 不能漏掉的条件 |
| --- | --- | --- |
| contexts、唯一 server、Node、Ref、事务及其关系 | `mb_lock` | 查找、摘表和计数变化同域；不能把全局表中的裸指针带到锁外继续访问。 |
| region 槽、backing 初始化、复制历史计数 | `region.lock`，部分语义还要求 `mb_lock` | 两把锁有重叠责任，不能只看字段所在结构就自行选择其中一把。 |
| 跨上下文提交、转换及内部 FREE | 先 `mb_lock`，再单个 `region.lock` | 当前不会同时持有两个 region 锁；调用辅助函数须符合其锁前提。 |
| mmap 和 VMA 回调 | mmap 只取 region.lock；VMA 数量为原子计数 | mmap 已处于 mm 锁环境，明确不取 mb_lock，避免反向依赖。 |
| 等待事务或等待 Server 工作 | 解开 mb_lock 后等待，醒来再核对状态 | 唤醒只是提示，返回和清理仍在锁下根据实际终态判断。 |
| 打开者身份 | context 持有 `struct pid`，ioctl/mmap 比较 TGID 对象 | 身份关联活到最终 release；不以可复用 PID 整数替代。 |

源码的 `mb_region_reserve` 和 `mb_region_free` 都注明调用方持有 `mb_lock`。后者还会归还 Node、Ref 持有，绝不只是释放 region 内部的一块内存。若仅因函数名包含 region 就从 mmap 路径调用它，会破坏锁前提。

特别看 C08 的 `mb_ref_build`：它在大锁保护下预留槽，把用户 payload 复制到接收 backing，再解析这个快照并转换。`mb_export_ref` 的控制输出也在大锁内，输出失败立即撤销。`mb_call_ref` 在摘除事务记录后，仍在锁内完成 reply 输出、交付/回滚和 active_calls 归还。

这些操作使用的是 mutex，因此不能笼统判成“在自旋锁里睡眠”。真实问题是某个坏页或慢缺页能长时间阻塞所有上下文；同时，若未来路径形成 `mb_lock → mm 锁` 与 `mm 锁 → mb_lock` 的闭环，还会死锁。当前 mmap 不取大锁，是有意保持的边界，而非可以随手统一的编码风格。

## 4. 比较三种并发方案

| 方案 | 好处 | 成本和适用范围 |
| --- | --- | --- |
| 保留大 mutex | 状态关系和回滚容易核对，适合固定容量的教学驱动 | 不相关上下文也互相阻塞；大锁内用户复制放大尾延迟。 |
| 按资源分域，短临界区配合临时持有 | 独立对象或进程可以并行，复制和较重回收可移出元数据锁 | 必须补全保活、重新验证、锁顺序和跨域提交协议。 |
| 原子/无锁结构加 RCU 等回收机制 | 某些热点读路径可降低锁竞争 | 只适用于有明确读写和回收模型的部分路径，不能替代跨表事务；学习和验证成本更高。 |

本章先选择第二种作为后续可实现方向，不要求把每个 mutex 换成 spinlock。先移出可以分阶段完成的慢操作，再测量是否仍有瓶颈。若固定负载下大锁已经满足目标，保留它并写清限制也是合理工程决定。

RCU 延后释放可让特定读者安全完成读取，但“读者能看”不意味着“读者可随意修改、继续调用或持有到任意时刻”。首次实现不同时引入新的无锁表和新的队列协议，便于把失败定位到一类改变。

## 5. 一份可实现的分域接口与锁序

第一轮设计仍用可睡眠 mutex，并限制跨上下文提交通过一个 `graph_lock` 串行化。它不是最终高并发架构，而是先把用户复制移出全局关系锁、保持关系提交可审查的中间版本。

| 概念锁/持有 | 保护或用途 | 规则 |
| --- | --- | --- |
| `graph_lock` | context 寻址、Ref/Node 关系变更、跨上下文提交与退出发布 | 需要它时必须最先取得；不能在 ctx 或 region 锁下反向获取。 |
| `ctx.state_lock` | 本上下文工作队列、事务终态、active/pending 及局部额度 | 同时取两个 context 锁时按不复用的 open_id 从小到大；普通路径优先只取一个。 |
| `region.lock` | 槽预留、提交、FREE 与 backing 状态 | 排在 state 锁之后；若确实需要两把，继续按 owner open_id 排序。 |
| `ctx_hold` / `node_hold` / `tx_hold` | 离开查找锁后的临时保活 | 必须在原保护下取得；最后归还可能触发回收，不能在仍需访问字段时提前 put。 |
| 退役队列 | 已不可寻址但还有持有的对象 | 最终释放在全部持有归还之后；队列持有本身也记账。 |

统一锁序可写为 `graph → state(open_id 升序) → region(open_id 升序)`。不需要 graph 的本地操作可以从后面的锁开始，但绝不再回头取 graph。任何辅助函数若需要升级到 graph，应先在安全持有下解锁，再按顺序获取并重新验证。

锁表必须为每个字段指定唯一责任，特别是 Node 的 owner/活性、Ref 表关系和 Node 队列并非一个字段。此处 Node 关系修改归 graph，active/pending 归 owner 的 state；需要两者一致时一起持有。带对象账本的 FREE 同样可能删除 Ref、归还 Node，因此要从 graph 开始，不能只取 region 锁再反向升级。元数据持有计数的最后释放由指定辅助函数处理，而不是各处任意 `--count` 后 `kfree`。

接口可分为 `lookup_and_hold`、`reserve`、`commit`、`abort`、`put` 五类。函数名和注释写明调用方需持哪些锁、是否可能睡眠、失败时谁仍持有输入资源；只写“线程安全”不足以指导调用者组合这些接口。

## 6. 把用户复制移到锁外，不能只移动那一行

提交路径可以分三段，每段结束时都有明确所有者：

1. **准备：**检查定长控制头和长度，复制 offsets 与正文到私有内核暂存区。暂存内存受每次请求上限约束；还要限制同时准备的总量，避免正式槽配额外出现无界内存。这里可以缺页或分配失败，但尚未发布任何请求。
2. **固定与提交：**按锁序定位源 Ref、目标及接收 context，取得持有，重新检查活性/授权/配额。从已经验证的快照转换对象，预留并填写接收 backing；所有失败资源进入本次账本。队列链接和额度提交构成唯一发布点。
3. **返回与释放：**成功后转移队列持有，释放临时快照和本地持有；失败只撤销本次预留。唤醒放在状态已可观察之后，不能先唤醒再建立记录。

如果为了进一步缩短锁时间，要在接收槽填充期间也放锁，则槽需要 `RESERVED` 状态和明确的 context/backing 持有；退出路径必须等待或取消准备者。重新加锁后必须确认“仍可提交”，否则释放预留。直接保存一个 `void *target` 解锁，然后假定退出没有发生，会把大锁原本提供的保活删掉。

接收端映射使字节的可见性比 RECEIVE 更早：C08 自己的线程可读 pending backing，不能把用户态“尚未收到 token”当成字节不可见的安全保证。新的分阶段设计仍须按第 13 章规则，先确定允许授予的对象，再向接收 backing 发布敏感内容。

控制输出又有不同风险。原先 IMPORT 输出失败可重试，CALL reply 输出失败要回滚未交付槽；移到锁外后，必须引入明确的“正在输出”持有与状态，防止同时 FREE、退出或第二次领取。不能假设 `copy_to_user` 要么完整成功、要么一个字节都没写；复制失败可能已有前缀可见，协议仍须靠内核状态拒绝越权和重复操作。

这一轮分域设计没有完成这些 ABI 细节，因此当前驱动继续采用已知的大锁契约。完整实现必须先补状态和回滚规则，再改锁覆盖范围；本文不把伪代码当作可直接合入的补丁。

## 7. 终态、FREE 和退出的共同不变量

| 不变量 | 正常路径 | 竞争或失败路径 |
| --- | --- | --- |
| 每笔事务只有一个终态 | 回复或错误被接受一次 | 取消/回复/退出在同一终态锁域竞争，后到者只观察既定结果。 |
| 每份持有归还一次 | 记录、槽、Ref 各自归还自己的单位 | 回滚只归还成功前缀；已交付槽不能被发送者取消抢回。 |
| 可寻址性和存活分开 | 活对象可查，持有保护使用过程 | 退出先摘寻址入口并标死，已有持有允许清理但禁止新提交。 |
| one-way 同 Node 只有一个 active | FREE 后最多取一个队头 | 重复 FREE 不推进；退出清理不再把死目标的队头交付。 |
| 容量包含预留与活资源 | reserve→commit→release | abort 归还预留；返回拒绝不能留下 in-use 增量。 |

退出采用“撤销、排空、等待持有、回收”四步：先禁止通过 open_id/Node 接受新工作；在正确锁域把未完成事务推进终态并摘队列；把需要较重清理的资源转给有持有的退役列表；最后一个持有归还时才真正释放内存。

唤醒应根据已经提交的状态执行，等待者醒来重新检查。若计划锁外唤醒，必须保留等待队列所在对象的持有；不能先 `put` 释放 context，再访问其中的 wait queue。延迟回收也须说明谁运行回收工作、模块卸载如何等待它完成。

当前 C08 的 VMA 持有文件，`close(fd)` 后仍存活的映射会延迟最终 release。测试若只关 fd 而不解除映射，不能把仍存在的 context 判为泄漏；也不能据此认为 close 已发出死亡通知。语义上的 Server 退出、最终文件释放和 backing 销毁是不同观察点。

## 8. 可运行观察：取消与回复必须只赢一次

仓库的确定性事务模型能分别重放两种次序，无需 root、VM 或驱动。在仓库根目录执行：

```sh
make build/transactions
timeout 5s ./build/transactions trace deliver reply cancel reap output_ok free_request free_reply
timeout 5s ./build/transactions trace deliver cancel reply free_request reap
timeout 5s ./build/transactions trace receive_fault deliver reply_fault reply reap output_fault free_request
```

第一条先接受回复，随后取消须显示 `accepted=0`；第二条先取消，迟到回复须拒绝；第三条分别演示接收输出、回复准备和调用输出失败的资源语义。每条正确运行均退出 0，最后应为 `records=0 request_slots=0 reply_slots=0 terminal_total=1`。不能把 trace 中受控故障的 `accepted=1` 误读为真实 ioctl 成功；它表示该失败事件适用于当前状态。

这些是顺序执行的 C 状态模型，没有并发线程，不证明 `mb_lock`、内存序或调度器实现正确。它们把“锁串行化之后必须得到哪两种结果”写成可以运行的判据，供真实竞争测试对照。模型进程结束后不留后台资源，二进制可保留供前面章节使用。

## 9. 故障矩阵：每一行都能说明如何停在现场

真实压力测试需要可控同步点，而不是依赖某个 `sleep` 恰好让线程撞上。下面是测试设计，不是新增可执行工具或已经跑过的报告；C08 有 `fail_after_register`、`fail_region_alloc` 两个既有注入参数，并不覆盖表中全部分配点。

| 故障/竞争 | 确定性前提和触发 | 必须观察的结果 | 实现覆盖边界 |
| --- | --- | --- | --- |
| 事务分配失败 | 第 n 次事务准备的分配点定向失败 | ENOMEM；无新事务、槽或目标持有 | 需要专用注入，不能用耗尽宿主内存代替。 |
| 输入复制失败 | 控制头有效，正文跨入 PROT_NONE 页 | EFAULT；转换成功前缀和预留全部撤销 | C08 可用坏用户地址检查其实际复制分支。 |
| 输出复制失败 | 已生成结果，输出页不可写 | 按 ABI 保持可重试或撤销未交付槽；不可重复交付 | IMPORT、RECEIVE、CALL 输出语义不同，分别核对。 |
| 对象转换中途失败 | `[有效 X, 无效 Handle]`；分别让 X 新建和复用 Ref | 旧持有保留，新单位为零 | C08 已有这种结构，不能只测第一个对象就失败。 |
| 队列或槽满 | 服务停在显式屏障，精确填到上限 | EAGAIN，拒绝不改变占用；FREE 后恢复 | C08 可观察 16 槽/64 事务；one-way 配额尚未实现。 |
| 取消与回复竞争 | 两线程先到同一屏障，再分别执行终态操作 | 恰一个终态，迟到者拒绝，记录/槽最终清零 | 两种赢家次序都需覆盖，不以出现任意赢家为失败。 |
| 转交与 owner 退出 | 转换前、提交后分别设置屏障退出 owner | 未提交则拒绝，已提交按持有/死亡规则清理 | C08 只有单 Server；多 owner 与死亡通知另验。 |
| FREE、close 与解除映射 | 已交付槽，分别控制 FREE、close 和最后 VMA 解除的次序 | 每份账目只还一次；映射存活时不提前最终释放 | 正在执行的 ioctl 自身持有 file，不能虚构同一 file 已被最终 release 的交错。 |
| FD 安装失败 | 预留接收 FD 后定向触发失败 | file 引用和预留号归还，无泄漏 FD | 当前不支持 FD，不能用对象测试替代。 |
| 延迟回收与卸载 | 活工作/映射存在时尝试卸载，再排空 | 按模块持有规则拒绝或等待；不访问已卸载代码 | 当前没有本章退役工作队列，未来需独立验证。 |

每次运行记录代码提交、内核配置及哈希、VM 资源、测试模式、随机种子、事件序列和截止时间。种子只能重放随机选择，不能复现任意 CPU 调度；遇到失败还应把关键顺序改造成带屏障的最小用例。原始日志要保留失败前的资源快照和最后一个成功事件。

分层执行先覆盖单线程正常/失败，再做同 context 多调用、跨 context 转交、退出混合；FD 和异步层在实际实现后加入。每层都比较前后活资源，而不是只看错误码或“没有崩溃”。活计数应恢复，复制字节等历史工作量不要求倒扣。

所有自动测试都应有总截止时间和清理阶段；清理必须先结束测试参与者和解除映射，再检查背景 observer 的最终计数，最后退出 observer。否则 observer 自己的 context 会被误判为泄漏。驱动故障实验只在可恢复 VM 内执行，不在宿主机加载实验模块。

## 10. KASAN 与 lockdep：证据分别覆盖什么

KASAN 为某些越界和释放后访问提供动态检测；lockdep 跟踪实际形成的锁依赖，帮助发现潜在死锁和错误锁使用。它们需要相应调试内核、配置和实际执行路径；打开日志后没有看到警告，并不证明运行的内核启用了检查。

验收应保留 `.config`、启动时的内核版本/配置证据、本轮完整内核日志、测试开始结束标记和失败重放条件。出现告警时保留第一条完整报告及其栈，而不是只统计最终程序退出码。一个先前内核的零告警日志不能替代改锁之后的新运行。

本章没有提供 KASAN/lockdep 成功记录；当前文档补齐也不关闭这些任务。今后即使两者零告警，也只能说“在该配置与覆盖路径下未报告问题”，不能说已经证明无竞态、无泄漏或所有退出次序都正确。

## 11. 性能：先定义测量的事件

吞吐必须分成接受速率、服务分发完成速率和业务效果完成速率。one-way 在前一秒接受 1000 条、只处理 100 条，不能报告为“业务吞吐 1000/s”。如果接受速率长期高于完成速率，观察到的只是队列增长或更晚的拒绝。

延迟也分开计时：同步调用的提交到回复，异步提交的调用到接受，队列提交到开始执行，以及开始执行到业务效果。使用单调时钟和内部请求 ID 关联事件；跨进程的本机时间可比较，仍要标明打点、调度和日志本身的开销。

| 要判断的问题 | 至少记录的数据 | 如何避免误判 |
| --- | --- | --- |
| 大锁是否阻塞不相关服务 | 锁等待/持有时长、目标 Node、复制字节、p50/p95/p99 | 分开看缺页与正常页；均值会掩盖少量全局停顿。 |
| 分域后吞吐是否增加 | 完成数/观察窗口、拒绝数、并发数、CPU 用量 | 使用同一负载和容量；不能把更大队列当成执行加速。 |
| 异步是否稳定 | 到达/接受/完成速率、队列深度、活字节、FREE 延迟 | 固定持续时间并包含排空阶段；积压应有界且可恢复。 |
| 调试成本有多大 | 同代码的调试配置和非调试配置分别测量 | 不混用 KASAN 与普通内核数字；结论注明环境。 |

先预热，再在固定窗口测量，重复同一配置并保存分布；改变锁、容量、线程数等变量时每次只改清楚的一组。闭环负载“上一笔完成才发下一笔”与固定到达率负载回答不同问题，报告须说明产生方式。

日志若每请求都同步输出，可能自己成为主要串行点。正确性阶段保留完整事件，性能阶段用有界采样或计数，并核对关闭日志是否改变负载语义。本章没有实际吞吐数据，因而不声称分域设计比大锁快多少。

## 13. 练习与带理由的核对

1. **把 `mb_lock` 替换成 spinlock 能否直接减少等待？**不能。现有临界区包含可能睡眠的用户复制和分配；先改状态/持有和分阶段流程，才有资格选择更窄的锁类型。
2. **Node 引用计数是原子的，查表后再加一是否安全？**不安全。查表锁释放后，最后一个持有可能先归还并释放对象；必须在安全保护下取得持有。
3. **取消和回复的测试只覆盖“回复赢”够不够？**不够。两种先后都合法，资源责任不同；分别重放并检查唯一终态与缓冲归属。
4. **KASAN 零告警且程序退出 0，能否关闭全部稳定性任务？**不能。还需确认配置、覆盖路径、资源账目、锁依赖与有界负载；动态工具没有覆盖所有调度。
5. **one-way 接受吞吐提高一倍，完成数不变且队列增长，算优化吗？**不能据此说执行能力提高。应一起报告积压、拒绝、端到端延迟和排空成本。

到这里，Node、Ref、事务、线程、缓冲和凭据都有了各自的责任，锁与持有负责让这些责任在并发下仍然成立。[下一章](16-binder-architecture.md)把这些需求带回真实 Binder，按“为什么需要这个结构、由谁保护、何时释放”阅读架构。
