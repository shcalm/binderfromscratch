    本地阅读站点：构建与验证¶

    本地站点使用 MkDocs Material，正文仍以 docs/ 中 Markdown 为单一来源。当前是开发阅读版，不代表 M1/M2/M3 正式发布。现有正文明确标注初稿，第 09–18 章只进入路线与任务。

    安装与预览¶

    在仓库根目录运行，使用 Python 3.10 或更新版本：

    python3 -m venv .venv/docs
.venv/docs/bin/python -m pip install --require-hashes -r requirements-docs.txt
.venv/docs/bin/python -m mkdocs serve --dev-addr 127.0.0.1:8000

    打开 http://127.0.0.1:8000/；端口已占用时将命令中的端口改为 8001。无需 sudo。若宿主 Python 缺少 ensurepip / venv 支持，已有 uv 时可直接复用其虚拟环境安装能力：

    uv venv --allow-existing --python /usr/bin/python3 .venv/docs
uv pip sync --python .venv/docs/bin/python requirements-docs.txt
.venv/docs/bin/python -m mkdocs serve --dev-addr 127.0.0.1:8000

    严格构建与链接检查¶

    .venv/docs/bin/python -m mkdocs build --strict --clean
.venv/docs/bin/python tools/site_check.py site
python3 tools/check-docs.py

    site/ 是可部署的静态产物，已经被 Git 忽略；.venv/ 和 artifacts/ 也已忽略。链接检查解析实际生成的 HTML，核对站内页面、目录入口、锚点、脚本、样式及搜索索引，不将构建成功等同于正文教学验收。外部 URL 单独计数，不声称网络有效性已检查；Android 对照保留版本与限制说明。

    依赖入口为 requirements-docs.in，requirements-docs.txt 固定包括传递依赖在内的版本及下载哈希。更新依赖时重新生成锁定文件并重跑构建和检查：

    uv pip compile requirements-docs.in --generate-hashes --output-file requirements-docs.txt

    源码与章节版本¶

    tools/site_hooks.py 在构建时生成 source/ 阅读页与目录页；这些页面只进入静态产物，不写回 docs/。正文、实验及报告中指向仓库源码的相对链接，通过 Markdown 解析树转到对应生成页。缺失的源码不会被伪造为阅读页，会由严格构建或静态链接检查报告。

    源码页有明确的仓库路径和工作树版本说明，展示本次构建时的源文本，不代表第 02 章固定提交。章节标签、环境和重放方式仍以代码版本索引为准。实验入口提供现有命令、预期证据和本地 diff 方法；尚无正式发布标签。

    静态预览与部署边界¶

    构建后可脱离 MkDocs 用普通 HTTP 服务检查产物：

    .venv/docs/bin/python -m http.server 8001 --bind 127.0.0.1 --directory site

    打开 http://127.0.0.1:8001/。实际托管时将整个 site/ 上传到支持目录 index.html 的静态服务器；子路径托管须保留全部相对资源和目录结构，再执行链接与浏览器检查。

    GitHub Pages 发布¶

    源码仓库为 https://github.com/shcalm/binderfromscratch，在线阅读地址为 https://shcalm.github.io/binderfromscratch/。mkdocs.yml 固定项目子路径，规范网址、站点地图及导航都使用同一地址；教程正文和代码仍维持开发版状态。

    发布工作流位于 .github/workflows/pages.yml。推送 main 或在仓库 Actions 中手动执行 Publish Tutorial，会安装带哈希锁定的文档依赖、检查 Markdown、严格构建并验证生成的链接/静态资源，然后通过 GitHub 官方 Pages artifact/deploy actions 发布 site/。工作流只申请读取代码、写入 Pages 和部署身份令牌的权限，不需要维护者额外保存 PAT 或 SSH 私钥。tutorial-development 用于开发，只有 main 自动发布；章节开发标签保持原样。

    当前网站已通过 gh-pages 分支发布。云端 Markdown 检查、严格构建和链接检查均已通过，但仓库默认的 github-pages 环境仅允许 gh-pages 部署，且工作流令牌无权修改 Pages 来源，因此 main 的自动部署尚需管理员完成一次设置：

    1. 在 Settings → Pages 将 Build and deployment 的 Source 改为 GitHub Actions。
    2. 在 Settings → Environments 打开 github-pages，检查 Deployment branches and tags，允许 main 分支部署。
    3. 在 Actions 中重跑最新的 Publish Tutorial 工作流，确认 Deploy GitHub Pages 成功。

    工作流将构建和部署拆成两个任务，环境限制不会阻止文档构建检查。完成上述设置前，可继续通过 .venv/docs/bin/ghp-import --no-jekyll --push --branch gh-pages --remote origin site 发布已验收的构建；切换后由 Actions artifact 负责部署。实际发布是否成功以部署步骤和线上网址响应为准，构建成功不等于已经上线。
